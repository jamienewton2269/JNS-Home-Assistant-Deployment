# JNS HA Steward — HA-General local automation reload access

Status (2026-10-24): root-only VM905 helper installed and audited; live V2 dry-run passed.
No administrator token is present yet and no Lux V2 automation edits have been applied.

## Architecture

- The existing host-based Steward service on Node B resolves ha-general / VM905.
- Gateway uses the existing trusted Node C -> Node B -> Proxmox guest-agent route.
- Helper: /config/.jns-steward/ha_reload_capability.py, root:root, mode 0700 inside VM905's HA Core container.
- Secret: /config/.jns-steward/ha_general_api.token, root:root, mode 0600. It is created locally only, not through GitHub or ChatGPT.
- Only http://127.0.0.1/api inside the HA Core container is used, never an external API host.
- Helper operation allowlist: status, authenticated probe, and automation.reload with prevalidated SHA-256 hashes of the known Lux configuration files.
- No arbitrary API method, URL or Home Assistant service is accepted.
- Operator can revoke the token from HA user profile Security at any time. The admin account remains powerful; protecting local backups and SSH/root access is necessary.

## One-time credential onboarding (human operator only)

1. On HA-General (NOT HA-Primary), create a dedicated login user jns-steward in Settings > People > Users. Give it Administrator rights (required to run automation.reload). A user-only account need not be linked to a person.
2. Sign in as that account, choose your User profile > Security > Long-lived access tokens > Create token. Name it JNS Steward - HA-General local automation reload.
3. Open the HA-General Terminal & SSH add-on, on VM905. Verify that you are root with id -u; it should print 0.
4. Run the following from that terminal; paste the token only at the hidden prompt:

    umask 077
    read -r -s -p 'Paste JNS Steward HA-General token: ' JNS_STEWARD_TOKEN; echo
    printf '%s' "$JNS_STEWARD_TOKEN" > /config/.jns-steward/ha_general_api.token
    unset JNS_STEWARD_TOKEN
    chmod 600 /config/.jns-steward/ha_general_api.token

Never paste the token into chat, GitHub, logs, command-line arguments, or a troubleshooting screenshot.

## Verification (does not reload)

From a trusted Node C GitHub read-only verification runner, execute the fixed helper's probe mode in the HA Core container. Do not invoke reload manually. It requires hashes generated by the JNS guarded deployment after backup and ha core check.

## Activation

Canonical workflow: .github/workflows/jns-lux-v2-steward-deploy.yml

Trigger by updating gateway/lux_manual_override/steward-v2-deploy.request only after token onboarding is locally verified.

Deployment transaction:
1. Steward status and authorised, read-only probe
2. Lux V2 guarded dry-run and optimistic file hash checks
3. Verified local backups and atomic config writes
4. ha core check (no restart)
5. Steward's fixed automation.reload capability
6. Verify exact expected automation entities; rollback and reload originals if unsuccessful

No HA-General restart. No new controller. Existing Bedtime, PIR and security automations untouched.

## Revocation / recovery

Revoke the credential in HA-General's dedicated user profile > Security.
Remove the local token file, verify the unauthorised probe fails, then rotate to a new token if required.
The helper code is independent of the token and never copies token data to the repository.
Full Home Assistant backups that include /config/.jns-steward require the same protection as an administrator credential.
